    Domain head, well-known containers and the AdminSDHolder template, read individually. Their inheritable bytes are what every object created directly below them receives.

    Containers ranked by inheritable payload

    Inheritable payload is the total size of the ACEs in a container's DACL that are marked to inherit (container or object inherit). A new object created directly below the container receives all of them before a single ACE of its own is added, so this number is the starting size of every future child. Containers above the warning threshold are propagation hotspots: fix them first, because every child inherits the problem.

    Trustees that fill the flagged descriptors

    Aggregated over every object at or above the warning threshold: which security principals own the most ACE bytes. One principal with thousands of bytes across many objects usually means per-object or per-user delegations that should be consolidated into a group with a single inheritable entry higher in the tree.

      How to read this report

      What is measured. The size in bytes of the self-relative nTSecurityDescriptor as returned by the domain controller: owner, primary group, DACL and (when the account may read it) SACL. This is the value the 64 KB limit applies to. Earlier tooling compared the length of the SDDL text, which can differ from the binary size by a factor of two or more and is not what the directory enforces.

      Why 64 KB. Access control lists in the directory are limited to 64 KB (65,536 bytes; the length field of a single ACL is 16 bits, so one ACL cannot exceed 65,535 bytes). A write that would push an object past the limit is rejected, typically with "The parameter is incorrect", and inheritance propagation cannot finish on that object.

      Where the bytes come from. Each ACE costs roughly 36 to 60 bytes (object ACEs with GUIDs are the large ones). Inherited ACEs are copied into every child, so a container with a large inheritable payload multiplies its problem across the whole subtree. Explicit per-object ACEs add up on individual objects; protected accounts receive the AdminSDHolder DACL on top.

      Headroom and "ACEs left". Headroom is 65,536 minus the measured size. The estimate of remaining ACEs divides the headroom by the object's own average ACE size. Treat it as an order of magnitude, not a promise.

      Typical remediation order. Start with the Propagation tab (largest inheritable payload, most flagged descendants), replace repeated per-principal delegations with group-based ones, remove inheritable ACEs that are no longer needed, and re-run with the JSON snapshot of this run as the baseline to confirm the trend.

      What this tool does

      How it measures

      • Binds over LDAP (System.DirectoryServices.Protocols) to the domain controller you name - never to the logon domain - with signing and sealing or LDAPS, and verifies the required server controls first.
      • Reads the raw nTSecurityDescriptor of every object in scope with the security-descriptor-flags control (owner, group, DACL and, when permitted, SACL) and measures its binary length, which is the value the 64 KB limit applies to.
      • Parses the descriptor header for every object (DACL and SACL size, ACE counts, protection flags) and walks the individual ACEs of flagged objects and containers to attribute bytes to inheritance, ACE type and trustee.
      • Reads the domain head, well-known containers, AdminSDHolder and the schema default descriptors separately, so that the starting size of new objects is known.
      • Writes a self-contained dashboard, a CSV, a JSON snapshot and a run log; the snapshot of one run is the baseline of the next.

      Scope and limits

      The tool is read-only and changes nothing in the directory. Sizes are exact for every object whose descriptor the account can read; objects without read access are counted as not measurable and the SACL is included only when the account holds the audit right on the domain controllers. Thresholds are configurable; the 64 KB limit itself is fixed by the directory. Findings should be verified against the object before permissions are changed.
